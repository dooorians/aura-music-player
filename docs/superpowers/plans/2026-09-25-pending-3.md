# Aura — three pending fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the three items left open after the P1 performance pass: the seek bar ignores the first gesture after the player opens; the player's lyric bubble "flashes" to a different glass look when its line changes; the committed P1 plan document carries machine-specific details.

**Architecture:** Three independent, local changes. (1) In `WavyProgressBar`, the tap and drag detectors are started undispatched inside the lazily-started `pointerInput` block, so they are already listening when the first pointer event arrives. (2) The lyric bubble keeps a fixed width (the column's full width), so a new lyric line no longer resizes its glass — a resize is what makes the glass re-sample live and change look. (3) The P1 plan document's absolute paths and device serial are replaced by neutral wording.

**Tech Stack:** Kotlin 2.2.10, Jetpack Compose (BOM 2026.02.01, Strong Skipping on), kotlinx.coroutines, AGP 9.4. Android app `com.ikko.aura`.

**Spec:** The user's request of 2026-09-25 ("corrige les 3 choses en attente") over the three items listed at the end of the P1 work: (1) lyric bubble — options 1 fixed width / 2 correct line from the first frame / 3 lighter glass; the user delegated the choice, ruling: option 1, as recommended; (2) the P1 plan document contains local paths and the device serial; (3) the first seek-bar drag after opening the player is ignored.

**Root cause of item 3 (established with on-device diagnostics before this plan, systematic-debugging Phase 1-3):** Compose starts a `pointerInput` block lazily, on the first pointer event. Inside it, `WavyProgressBar` starts its two detectors with a plain `launch { }`, which is *dispatched* — so they begin listening only after that first event has been delivered, and miss the whole first gesture. The player page's own `detectDragGestures` (running directly in its block) receives it instead and reads a rightward drag as "previous track" (which restarts the track past 3 s). Logs: first drag → `bar pointerInput START`, `page DRAG START … dx=477`, no bar event; second drag → `bar DRAG START`, `vm seekTo`. With both launches `CoroutineStart.UNDISPATCHED`, the first drag sought 0:10 → 2:38 and the page detector stayed silent.

## Amendment (after Task 4 Step 4 failed)

Task 4 Step 4 measured the bubble's glass on the device (per-frame difference of a patch of the bubble's glass after the card lands, `sauts >= 1` = frame-to-frame jumps of at least 1 grey level): with Task 2 the glass still jumped by ~3.5 levels ~150 ms after landing, exactly as before Task 2. Task 2's premise (a resize) was wrong. Systematic debugging, one variable at a time, on the release build:

| Bubble enter transition | Jumps after landing |
|---|---|
| fadeIn + scaleIn(0.92) (current) | 3.7 (twice), 3.5 |
| scaleIn(0.92) alone | 3.7 |
| none | none |
| fadeIn alone | none (twice) |

**Root cause:** the lyrics arrive after the player is built, so the bubble usually appears *while the card rises* — the moment the glass takes the picture it keeps for the rest of the rise (`GlassSettle`: it samples where each panel will rest, from the panel's position in the window). A bubble still scaling up from 92% is a few pixels from where it will rest, so its glass takes a slightly wrong picture and corrects itself once the card lands: the flash. A fade does not move the bubble.
